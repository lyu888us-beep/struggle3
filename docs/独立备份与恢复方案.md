# 独立备份与恢复方案（设计草案，尚未实施）

更新：2026-11-03。适用于当前共享 Worker `rongyu-shared-backend` 的 SQLite Durable Object `rongyu-shared-data-v1`。本文不是生产操作指南；当前没有经过验收的导出或恢复工具，不能据此认定已经有备份。

## 目标与边界

- 在不中断或经批准短暂停写的前提下，取得同一时间点的一致数据，经过额外加密后保存到 Windows 电脑和移动硬盘；备份数据与解密密钥分开保管。确定频率和保存期限时先确认可接受的数据丢失时间、恢复时间及保管义务。
- 独立副本必须离开 Cloudflare。Cloudflare 的 Durable Object 时间点恢复（PITR）可作为附加恢复手段，但不是独立备份；手机离线档案、ZIP、管理端 CSV 都不是完整数据库备份。PITR 在本地开发环境不可用。参见 [Cloudflare SQLite 存储 API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)。
- 禁止把正式数据库、密钥、下载链接或客户数据发到聊天、GitHub 或第三方测试服务。生产数据只由授权人员处理。不得替换现有 `DATA_ENCRYPTION_KEY` 或 Web Push 密钥。

## 当前源码盘点

数据库表包括 users、user_identity_vault、security_settings、sessions、items、attachments、messages、message_attachments、push_subscriptions、push_deliveries 和 blob_chunks。需在导出时实际枚举并核对，而非只依赖这份清单；还要考虑架构、索引、触发器、SQLite 自增序列与未来新增表。图片可能由附件表中的 `RYB2:` 引用指向 blob_chunks，缺少这些块将造成无法恢复图片。账户、会话和推送订阅均属敏感数据；恢复后是否保留会话和推送需要明确的安全策略。

当前代码通过 DO 的存储 API 使用 SQL，另有用于提醒的 alarm；应确认运行版本有没有其他 KV 或状态。恢复测试应检查定时器重建、推送去重及发送行为，在隔离环境禁用真实推送和外发。数据库本身并非所有字段或元数据都加密，必须对整个导出文件额外加密。

## 待实现的安全方案

1. 先验证 Cloudflare 当前可用的 DO 完整导出能力；不能将 D1 导出接口用于此 DO。若需开发专用导出通道，必须设计独立强认证、最小权限、限时启用、审计及禁缓存，不使用公开链接，不把密钥放进源码；先审查其攻击面。
2. 快照必须跨所有表保持一致：评估 DO 事务、数据体积、执行时间和内存限制。不能将多次分页读取直接当成一致快照；必要时先设计经用户同意的停写窗口或安全快照机制。避免把大图片一次性全部载入内存。
3. 加密文件应使用成熟、经过认证的加密格式及可靠口令派生，完整性验证应覆盖整个备份及清单；禁止自行发明加密协议。核实 Windows 可用性和成本后再选工具。下载途中、临时文件和解密恢复阶段也应防止明文泄漏。密钥丢失意味着无法恢复。
4. 制定版本化清单：生成时间、源码及数据库结构版本、各表记录数、文件完整性和附件块引用校验；清单自身可能包含敏感元数据，应保护。保留原有加密数据，不能只导出解密后的业务页面。
5. 导入只针对全新隔离 DO，绝不默认覆盖正式 `STORE`。恢复工具需支持失败即停止、核验和重新演练；SQL、KV、索引、触发器、序列及 alarm 的具体恢复方式须验证平台限制。密钥由用户在隔离环境自行配置，测试只使用新建测试密钥。
6. 虚构数据演练覆盖：账号和登录、图文及多块大附件、消息、关系完整性、正确/错误密钥、损坏和截断文件、备份期间写入、恢复后新增记录、重启、推送禁用和提醒状态。逐项记录，不通过不得宣称可恢复。
7. 用户确认生产备份及上线之前，另行制定安全的操作步骤、恢复与回滚方案；首次正式备份和恢复测试应由授权人员执行并确认，不能将本地虚构演练等同正式数据已备份。

## 需要用户确认

- 最多可接受丢失多久的数据？能否安排短暂停写窗口？
- Windows 电脑及移动硬盘是否都有足够空间？是否能保留另一份异地加密副本？
- 一位管理员是否被授权在线查看全部客户？哪些客户资料不应被其访问？
- 短信和邮件服务商名称、开通情况、可用地区以及已验证发信域名；无需提供任何密码或密钥。
